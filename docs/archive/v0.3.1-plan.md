# v0.3.1 Plan: correctness and CLI trust

## Release intent

`v0.3.1` is a patch release focused on correctness, result classification, and
CLI/runtime contract fixes. It should not broaden `tsmi`'s product scope or add
new output artifacts. The goal is to make existing behavior trustworthy for
library consumers, CLI users, and automation.

This release maps directly to GitHub milestone `v0.3.1`:

- `#1` CLI exits 0 even when modules are reported missing
- `#2` CLI compile path does not apply configured reader options
- `#3` Compiler can emit modules whose non-base imports failed to resolve
- `#4` Distinguish HTTP/network failures from true missing MIBs

## Implementation status

Implemented locally on `2026-05-06`. Release/tagging is still pending.

Completed behavior:

- CLI exits with code `1` when any module result is `missing` or `failed`
- `_compile_async()` passes configured size, timeout, retry, and cache options
  into the real readers it constructs
- `HttpReader` preserves true not-found outcomes as `MibNotFoundError` and
  classifies transport/server exhaustion as `NetworkError`
- modules blocked by unresolved non-base imports are marked `failed` and are
  not emitted to disk

Local validation completed:

- `pytest` -> `358 passed`
- `ruff check .` -> clean
- `mypy trishul_smi` -> clean

## Scope decisions

### 1. No new public status values in `v0.3.1`

Keep `CompileResult.status` as:

- `compiled`
- `missing`
- `failed`

Do **not** add `skipped`, `blocked`, or similar in this patch release.

Interpretation for `v0.3.1`:

- `missing` = genuine not-found outcome
- `failed` = parse error, writer error, network/server error, or unresolved
  non-base dependency

This keeps the public result surface stable while fixing the incorrect behavior.

### 2. Missing vs failed semantics must be tightened

Current semantics are too loose. `v0.3.1` should define them explicitly:

- If all configured sources genuinely miss a MIB, report `missing`
- If at least one configured source had a non-not-found failure and no source
  succeeded, report `failed`
- If a module depends on a non-base import that did not resolve, the dependent
  module must be `failed`, not `compiled`

### 3. CLI exit codes must reflect unfulfilled work

For `v0.3.1`, the CLI should exit non-zero if **any** result is `failed` or
`missing`. Do not special-case dependency-only missing in this release.

Rationale: if the compile result set is incomplete, automation should not
receive exit code `0`.

## Actionable items

### 1. Fix CLI reader wiring (`#2`)

Source:

- `trishul_smi/cli/main.py`
- `trishul_smi/reader/localfile.py`
- `trishul_smi/reader/httpclient.py`

Problem:

`CompilerConfig` receives CLI option values, but `_compile_async()` constructs
readers with defaults:

- `FileReader(d)`
- `HttpReader(*config.sources)`

This silently drops:

- `max_mib_size`
- `http_timeout`
- `http_retries`
- raw HTTP cache settings

Planned change:

- pass `max_size=config.max_mib_size` into `FileReader`
- pass `timeout=config.http_timeout` into `HttpReader`
- pass `retries=config.http_retries` into `HttpReader`
- pass `max_size=config.max_mib_size` into `HttpReader`
- pass `cache_dir=config.cache_dir` and `cache_ttl_days=config.cache_ttl_days`
  into `HttpReader`

Tests:

- add CLI-level regression tests that assert `_compile_async()` constructs
  readers with config-derived values
- do not broaden this issue into retry-semantics redesign unless a regression
  is proven during implementation

### 2. Distinguish HTTP/network failures from missing (`#4`)

Source:

- `trishul_smi/reader/httpclient.py`
- `trishul_smi/errors.py`
- `trishul_smi/reader/chain.py`

Problem:

`HttpReader.fetch()` currently collapses non-404 failures into
`MibNotFoundError` after trying all sources. This destroys the distinction
between "not found" and "source unavailable/unhealthy".

Planned change:

- use `MibNotFoundError` only for genuine miss outcomes
- use `NetworkError` for:
  - transport errors
  - timeouts
  - TLS/DNS/connectivity failures
  - non-404 HTTP failures after retry/fallback exhaustion
- preserve fallback behavior across multiple sources

Decision for mixed outcomes:

- if all sources miss with 404/not-found semantics -> `MibNotFoundError`
- if any source has a non-not-found failure and no source succeeds ->
  `NetworkError`

Tests:

- transport error classification
- 5xx classification
- mixed-source behavior (404 + 5xx should not become `missing`)
- existing 404 fallback tests must continue to pass

### 3. Block compilation of modules with unresolved non-base imports (`#3`)

Source:

- `trishul_smi/resolver/resolver.py`
- `trishul_smi/compiler.py`
- possibly `trishul_smi/resolver/dependency.py`

Problem:

The current resolver/compiler combination can emit a module as `compiled` even
when one of its non-base imports failed to resolve.

Planned behavior:

- a module whose non-base imports are unresolved must not be emitted as
  `compiled`
- blocked dependents become `failed`
- error text should identify the unresolved import(s)

Recommended implementation approach:

- compute unresolved non-base dependencies before code generation
- propagate blocked status transitively through the resolved module set
- exclude blocked modules from the "successfully compiled" path
- append explicit `failed` results for blocked modules

Preferred compatibility approach for `v0.3.1`:

- no new result status
- no partial code generation for blocked modules

Tests:

- requested module with missing dependency -> dependent becomes `failed`
- transitive blocking behavior (A depends on B depends on missing C)
- blocked modules are not written to disk

### 4. Fix CLI exit semantics for missing results (`#1`)

Source:

- `trishul_smi/cli/main.py`
- `trishul_smi/models/result.py`

Problem:

The CLI exits non-zero only when any result is `failed`. `missing` results do
not affect the exit code.

Planned change:

- exit `1` if any result is `failed` or `missing`

Tests:

- missing-only run exits `1`
- mixed compiled + missing exits `1`
- compiled-only run still exits `0`

## Risks and guardrails

### Risk 1: over-expanding patch scope

Do not fold unrelated runtime redesign into `v0.3.1`. Keep this release about
fixing trust and behavior.

### Risk 2: changing public API too much

Avoid new result statuses or broad type-surface changes in this patch release.
Prefer clearer error strings and corrected status assignment.

### Risk 3: changing HTTP semantics without tests

`HttpReader` classification changes will affect downstream status behavior.
Implementation must land with explicit transport/5xx/mixed-source tests.

### Risk 4: dependency blocking can cascade

A single missing dependency can invalidate multiple dependents. This is correct,
but the error messages must make the cascade understandable.
