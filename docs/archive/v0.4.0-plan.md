# v0.4.0 Plan: runtime bundle contract and JSON sidecars

## Release intent

`v0.4.0` is a minor release focused on defining the runtime-facing contract of
`tsmi` JSON output for downstream consumers such as future `tsnmp` tooling.

This release is about **locking the producer contract around the existing JSON
output** and then adding sidecars that improve determinism and performance. It
should not rework the compiler pipeline itself.

This release maps directly to GitHub milestone `v0.4.0`:

- `#8` Define runtime bundle contract: module JSON is atomic, sidecars optional
- `#5` Generate `oid_index.json` for fast reverse OID lookup
- `#6` Emit a bundle manifest for compiled JSON output
- `#7` Version the JSON IR for downstream consumers

## Release theme

`v0.3.1` is about correctness and trust.

`v0.4.0` is about making `tsmi` a stronger producer for downstream consumers by
standardizing:

- the atomic module JSON contract
- the meaning of a "bundle"
- the role of sidecars like `manifest.json` and `oid_index.json`
- the versioning metadata that downstream runtimes can trust

## Scope decisions

### 1. Module JSON is the atomic usable artifact

Every emitted module JSON file must be individually loadable and usable as the
source of truth.

Implications:

- a single `IF-MIB.json` is valid runtime input
- module JSON does not require `manifest.json` for correctness
- module JSON does not require `oid_index.json` for correctness
- sidecars must never become the only source of semantic truth

This is the core contract defined by `#8`.

### 2. A bundle is a logical set of module JSON files

A bundle is **not** defined as "a directory containing `manifest.json` and
`oid_index.json`".

Instead, a bundle is one or more compiled module JSON artifacts.

Valid bundle shapes include:

- a single module JSON file
- a directory of module JSON files
- a directory of module JSON files plus `manifest.json`
- a directory of module JSON files plus `manifest.json` and `oid_index.json`

A single module JSON file is therefore a valid degenerate bundle.

### 3. `tsmi` JSON becomes an explicitly versioned IR

Current module JSON already has stable-looking structure, but it does not carry
an explicit IR/schema version. `v0.4.0` should make that contract explicit.

Planned additions to every module JSON:

- top-level `schema_version`
- top-level `producer_version`
- keep `generated_by`
- keep `generated_at`

Compatibility policy for `v0.4.0`:

- additive fields within the same `schema_version` are allowed
- incompatible structural changes require a `schema_version` bump
- downstream consumers should be able to reject unsupported versions explicitly

### 4. `manifest.json` is optional bundle metadata

`manifest.json` should describe a bundle directory declaratively, but must not
be required to interpret the module files.

It is metadata, not a correctness dependency.

Rules for `v0.4.0`:

- if emitted, it should list only successfully emitted module JSON files
- it should use deterministic ordering
- it should reference filenames, not absolute paths
- it should never override module-file contents

### 5. `oid_index.json` is optional performance metadata

`oid_index.json` should be a reverse-lookup accelerator only.

It is derived metadata, not a source of truth.

Rules for `v0.4.0`:

- if emitted, it must be derivable from module JSON
- it must not be the only place an object is described
- downstream consumers must be able to rebuild or ignore it safely

### 6. Compile-time strictness is separate from runtime flexibility

Compile-time:

- broken or semantically untrustworthy modules should not be emitted
- sidecars should enumerate only successfully emitted module JSON files

Runtime:

- downstream consumers may later load only `IF-MIB.json`
- sidecar absence must not invalidate module JSON usage
- missing companion modules may reduce enrichment fidelity, but should not make
  the existing module JSON artifact itself invalid

## Actionable items

### 1. Define and document the runtime bundle contract (`#8`)

Source:

- docs in `docs/design-notes.md`, `docs/architecture.md`, `docs/cli.md`
- release planning and artifact semantics

Problem:

The downstream contract is still ambiguous around whether module JSON is
individually usable and whether sidecars are required.

Planned change:

- document module JSON as the atomic usable artifact and source of truth
- document a bundle as one or more module JSON files
- document `manifest.json` as optional bundle metadata
- document `oid_index.json` as optional performance metadata
- document compile-time strictness separately from runtime partial-bundle
  flexibility

Tests/docs acceptance:

- docs explicitly state that a single module JSON file is valid runtime input
- docs explicitly state that sidecar absence does not make module JSON unusable

### 2. Version the module JSON IR (`#7`)

Source:

- `trishul_smi/output/json_fmt.py`
- docs in `docs/cli.md`, `docs/design-notes.md`, `docs/architecture.md`

Problem:

Module JSON has no explicit schema/IR version, so downstream consumers must
infer compatibility from field presence.

Planned change:

- add `schema_version` to every emitted module JSON
- add `producer_version` derived from the installed package version
- document JSON IR compatibility rules

Deliberate non-goal for `v0.4.0`:

- do not require a full machine-readable JSON Schema document unless it turns
  out to be cheap after the runtime-facing metadata is in place

Tests:

- module JSON contains `schema_version`
- module JSON contains `producer_version`
- these values are stable and documented

### 3. Emit a bundle manifest (`#6`)

Source:

- compile output path / writer flow
- docs in `docs/architecture.md`, `docs/design-notes.md`, `docs/cli.md`

Problem:

There is no single machine-readable file describing a compiled JSON directory as
a coherent bundle when one is emitted and distributed as a set.

Planned artifact:

- `manifest.json`

Minimum manifest contents:

- bundle `schema_version`
- `producer_version`
- `generated_at`
- deterministic `modules` list
- companion artifact references, including `oid_index.json` when present

Recommended shape:

- module list should be sorted deterministically
- manifest should reference filenames, not absolute paths

Decision for `v0.4.0`:

- emit `manifest.json` only when `json` output is requested
- include only successfully compiled JSON modules in the bundle inventory
- treat `manifest.json` as additive metadata, not a correctness requirement

Tests:

- manifest file exists for JSON output
- module ordering is deterministic
- manifest references companion artifacts correctly

### 4. Generate `oid_index.json` (`#5`)

Source:

- compile output path / writer flow
- docs and future runtime assumptions

Problem:

A runtime consumer currently has to scan every module file to build reverse OID
lookup structures.

Planned artifact:

- `oid_index.json`

Minimum index requirements:

- key: resolved OID string
- value: object metadata sufficient for reverse lookup, at least:
  - `module`
  - `object`
  - `class`

Optional-but-likely useful fields:

- `object_type`
- `nodetype`

Decision for `v0.4.0`:

- include objects and notifications where relevant
- keep the first version flat and deterministic
- prefer one obvious lookup shape over a richly normalized schema
- treat `oid_index.json` as additive derived metadata, not a correctness
  requirement

Open implementation caution:

If duplicate OIDs are discovered in real-world bundles, the artifact shape may
need to support multiple entries per OID. Validate this during implementation
before locking the exact payload.

Tests:

- `oid_index.json` is emitted for JSON output
- representative object and notification lookups resolve correctly
- index ordering/content is deterministic

## Risks and guardrails

### Risk 1: accidental format churn

The whole point of `v0.4.0` is to make the JSON contract more explicit.
Avoid unnecessary renaming or restructuring of existing module payloads.

### Risk 2: overbuilding the bundle layer

Do not turn sidecars into correctness dependencies. Keep module JSON as the
source of truth and keep `manifest.json` focused on bundle discovery and
compatibility.

### Risk 3: uncertain duplicate-OID semantics

Real-world MIB corpora may contain aliases or collisions. Confirm whether a
single-entry OID index is sufficient before freezing the exact `oid_index.json`
shape.

### Risk 4: partial compile output ambiguity

Bundle artifacts should not imply a complete successful build when the compile
run itself failed. If necessary, constrain artifact emission to successful JSON
compilation runs or clearly document that manifests enumerate compiled modules
only.
