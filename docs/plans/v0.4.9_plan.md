# v0.4.9 Plan — Runtime Robustness & Concurrency

**Theme:** safe as an embedded async service. The review's concurrency and cache-correctness
findings, plus the two long-open cache issues that touch the same code.

**Status:** planned

## Issues in scope

| Issue | Title | Notes |
|-------|-------|-------|

## Review residue (from the v0.4.8 implementation review)

Small reader-side items found while reviewing v0.4.8; fold into this release's cache/robustness scope:

| Item | Notes |
|------|-------|
| HttpReader raw-body cache is write-only | Nothing reads `cache_dir/raw/` back since the ETag/304 removal — remove `_write_cache` + the reader's `cache_dir` param (or make it an explicit debug dump), and fix the two tests pinning the dead artifact. |
| Nested-zip aggregate scan cap | Per-entry reads are bounded, but an archive with many small nested zips causes bounded-memory time/disk churn; add an aggregate cap (#17 follow-up). |
| `cache_ttl_days` on HttpReader | Accepted-but-unused since #18; emit a `DeprecationWarning` for Python-API users before removal. |

## Non-goals

- Parser correctness (v0.4.7); reader/HTTP behavior (v0.4.8); output formats (v0.4.10).

## Acceptance criteria

- Parse demonstrably runs off the loop thread (thread-id capture test).
- Two concurrent `compile()` calls on one `MibCompiler` → each output carries its own
  metadata (test).
- Same cache entry written concurrently → no corrupt entry survives (test).
- Cache `PermissionError` / TOCTOU `FileNotFoundError` on read → miss, compile succeeds (test).
- `status="cached"` round-trips correctly and is surfaced by the CLI without breaking the
  missing/failed exit-code contract.
- Updated source file invalidates cache (fingerprint or equivalent, per #12).
- Release gate per `docs/release-checklist.md`.
